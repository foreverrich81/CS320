# CS320
Software Testing

You can keep your code functional and secure by combining good testing habits with solid defensive programming. Start by turning the requirements into tests that checks them directly. Write tests that check valid inputs, invalid inputs, and edge cases so you know the program behaves correctly in every scenario. Use coverage tools to help reveal untested branches or missed validation paths and Keep the logic simple, like using HashMaps for fast lookups.

On the security side, the most important step is validating every input. Never assume data is safe or well‑formed. Make sure the program checks for things like null values, length limits, proper formats, and immediately throw a clear exception whenever something isn’t valid. Keeping identifiers immutable prevents accidental or unauthorized changes, and keeping internal data structures private protects them from being modified outside the class.

I interpret the user needs by understanding what the user is really trying to accomplish, then translating those needs into clear, testable requirements and finally building code that enforces those requirements. Users often describe vague or incomplete needs, so the first job is to clarify the problem they want solved. Once their goals are understood, I can convert them into specific rules that the software must follow. These requirements then become the foundation for the tests and code written. Write tests that verify each rule With those expectations clear, build simple, predictable logic that enforces the rules and prevents invalid behavior. Finally, I validate my interpretation by checking that the finished behavior matches what the user actually needs.

Designing software is really about moving from a vague idea to a clear, working solution in a structured, intentional way. Start by understanding what the user actually needs. Once I understand the problem, I translate those needs into specific requirements. The requirements give me the boundaries, rules, and behaviors the program must follow. After that, I refine the requirements to remove anything ambiguous or contradictory. I then move into design, where I figure out “how” the system should work. This is where I sketch out the structure, choose the components, and decide how everything fits together. Once the design is clear, I implement the code, keeping the logic simple and aligned with the requirements. Finally, I verify the software by writing tests based directly on those requirements to ensure the program behaves exactly as intended.
